## Compatibility details

- `MapsInCoolDown` keeps the existing current-map-plus-N-previous-entries capacity. Zero disables automatic history, but the existing explicit administrator cooldown command can still add an entry until the next map-list refresh. No file is rewritten, migrated or deduplicated. The module-directory `maplist.txt` contract, `name:WorkshopNumericID`, comments and exact duplicate rows remain unchanged.
- Workshop identity is inferred **only** from unambiguous names/IDs in the loaded map list. If `Server.MapName` is an unknown internal filename, no current Workshop ID is guessed. Such a map retains ordinary case-insensitive name matching; its unknown aliases cannot yet be reliably excluded. Native acceptance must check actual server names versus the shared map list.
- A subsequent automatic vote needs the relevant configured trigger condition to become false and then true again. A normal extension that raises remaining time above `TriggerSecondsBeforeEnd` rearms the time trigger, which fires when it later crosses that threshold. Round triggers similarly rearm after leaving their configured threshold. A completed extension observes that exit before the next round can decrement the limit; monitoring can rearm round conditions but only RoundStart starts a round-based ballot. Starting any map ballot consumes both currently armed trigger episodes, including manual/RTV ballots that finish between monitor ticks.
- If `ExtendTimeStep` is zero, changes a different time limit, or is too small to leave the trigger threshold, the monitor does **not** start an endless vote every second, including with `ExtendLimit = -1`. Use manual RTV or an extension sufficient to leave the relevant threshold. No new arbitrary cooldown interval or forced extension amount is invented.
- The RTV cooldown uses monotonic elapsed time and persists through normal map changes in the same plugin instance. Map start immediately resets pending RTV requests, without a delayed timer that can erase new requests. The former automatic self-reload workaround is removed because dependencies already reset map state; manual plugin reload/server restart still resets in-memory cooldown and history. No new on-disk player data is introduced.
- Plugin.Load no longer calls MapLister.OnLoad twice: DependencyManager already initializes it. Legitimate repeated map plays remain distinct history entries; no permanent same-name deduplication hides initialization errors.
- Executed one-shot map-change timers retire only their own wrapper before callback work. Later cleanup cannot kill that completed timer through a stale native pointer, and an old callback cannot retire a replacement timer. Completed wrappers and successfully killed owned timers are also removed by object identity from the public CSS379 `BasePlugin.Timers` list, so host unload does not re-kill them. Failed kills retain ownership for retry. No internal reflection or whole-list clearing is used. On managed map start, old STOP_ON_MAPCHANGE timers are only abandoned/forgotten because CSS has already deleted them; failed old-map Kill actions are not retried against recycled pointers. This covers the map-transition, map-vote, VIP extension, automatic monitor and delayed GameRules refresh owned here.
- The delayed GameRules refresh is now a plugin-owned, generation-guarded one-shot that stops on map change and unload, rather than an untracked native timer. Automatic threshold observation waits for real game rules instead of treating default values during refresh as match state.
- Automatic timer callbacks are generation-guarded. Failed cancellation invalidates callback work immediately and retains the owned cancellation action for retry; it does not silently start another timer. Startup rollback/unload now explicitly stop this monitor alongside vote/map/menu cleanup.

## Validation and remaining gates

The local managed suite has **333 checks**, including the previous 233. It builds against the real CSS379 assembly, checks compiled TypeRefs for removed schema types and exercises production policy classes. Menu-object initialization and event subscriptions are managed tests; they do not simulate a native controller or prove that game events/rendering work in CS2. Reproduce with the build/test commands in [screen-menu notes](CSS379_SCREEN_MENU.md). CI is build/managed-tests only, never deployment.

Before any deployment, perform the existing [screen-menu native gates](CSS379_SCREEN_MENU.md#native-acceptance-gates-before-deployment) and [main-backport gates](CSS379_MAIN_BACKPORTS.md#validation), plus:

1. Check actual `game_type`/`game_mode`, time/round convars, loaded map-list location and server map names. Do not infer present server mode from historical [custom-mode reports](https://github.com/Oz-Lin/cs2-rockthevote/issues/23#issuecomment-2809574216).
2. Exercise zero map history in chat, HTML and screen modes; alias rejection through menus, full names and partial queries; normal and Workshop-ID map changes without modifying the map list.
3. Complete RTV, change map, and verify the remaining configured cooldown and immediate request reset. Verify zero cooldown and server-initiated RTV as well as player commands.
4. On time-based long-round/custom servers: vote, extend above the threshold, wait until it is crossed again, then finish a second automatic vote without a round event. Also test short/zero-time and round-only extensions that remain inside the threshold, unlimited extension configuration, round restarts, map changes, unload and timer failure logging.
5. Retain the optional-pause concurrency and synchronous-nextlevel engine-consumption limitations described in the main-backport notes. No native acceptance or server deployment is claimed here.

The public timer-list behavior was verified against [CSS379 BasePlugin.cs](https://github.com/roflmuffin/CounterStrikeSharp/blob/f58e383/managed/CounterStrikeSharp.API/Core/BasePlugin.cs). Native timer allocation/cancellation ordering still requires game acceptance.
